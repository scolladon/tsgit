# 503 — Bench size taxonomy: one generator, packed small/medium/large, loose read preserved as a micro-scenario

- **Status:** accepted (user judgment — ratified packed small-tier + retention of the loose
  read path over dropping it or keeping loose-tmpdir small)
- **Date:** 2026-07-24
- **Design:** docs/design/bench-hot-path-rework.md · **Refines:**
  [ADR-471](471-deep-delta-chain-bench-fixture.md), [ADR-474](474-bench-fixture-generator-topology.md)
  (the deterministic scaled-fixture generator this taxonomy extends)

## Context

The current bench suite has no consistent size taxonomy: "small" means both
`setupSmallRepo` (50 commits, **loose** objects, tmpdir-per-run) and `setupDeepAncestryRepo`
(200 commits); "medium/large" come from a *separate* generator (`fixture-generator.ts`,
`MEDIUM_FIXTURE` = 5k commits / 20k blobs / ~50 MB **packed**; `LARGE_FIXTURE` = 50k / 200k /
~500 MB, env-gated). So today storage shape (loose vs packed) and size both vary across
"tiers" — exactly what a clean tier taxonomy must not do. 27.4 requires hot paths to run at
three size tiers.

## Options considered

1. **One generator, packed small + medium + large, size-only variation; shape orthogonal;
   loose read kept as a named micro-scenario** (design recommendation) — add a first-class
   `SMALL_FIXTURE` to the scaled generator so all three tiers share one topology and cache
   mechanism, varying only size; preserve the loose-object read path as one explicitly-named,
   non-tiered micro-scenario. / pros: isolates size as the tier variable; no coverage lost.
   / cons: small becomes packed, so the loose path moves to a dedicated scenario.
2. **Packed small, drop loose read** — cleanest tiering. / cons: loses the loose-object
   cold-read path entirely — a real coverage loss.
3. **Keep loose-tmpdir small** — small stays loose. / cons: tiers differ in storage shape
   *and* size, keeping the current incoherence.

## Decision

Three size tiers, all generated by the **one** `fixture-generator.ts`, **packed**, varying
**only** commit/blob counts:

| Tier | commits | blobs | ~size | runs in |
|---|---|---|---|---|
| **small** | ~50 | ~200 | <1 MB | every run + PR gate |
| **medium** | 5 000 | 20 000 | ~50 MB | nightly + PR gate |
| **large** | 50 000 | 200 000 | ~500 MB | `TSGIT_BENCH_LARGE` (nightly/manual) |

`medium`/`large` are today's `MEDIUM_FIXTURE`/`LARGE_FIXTURE` unchanged; the new work is a
first-class `SMALL_FIXTURE` in the scaled generator. The **loose-object read path** is
preserved as **one explicitly-named non-tiered micro-scenario** (a fresh small loose repo),
so no coverage is silently lost. Fixture **shape** (multi-file, deep-ancestry, evolving-delta,
tag preamble) stays **orthogonal** to size: a hot operation is tiered in its representative
shape (`blame` → deep-ancestry × {small,medium,large}; `describe`/`name-rev` → multi-file ×
tiers + their `git` preamble).

## Consequences

- Size is the only variable across tiers, which is the point of tiering.
- `SMALL_FIXTURE` and a `deep-ancestry` scaled strategy are added to `fixture-generator.ts`;
  `FIXTURE_GENERATOR_VERSION` bumps, invalidating **all** cached tiers once (the next nightly
  regenerates the ~500 MB large fixture a single time; the `actions/cache` key follows the
  file hash).
- `fixtures.ts` (`setupSmallRepo`, `setupDeepAncestryRepo`) is superseded for tiered
  operations; retained only where the generator cannot express a scenario (e.g. the
  dirty-working-tree `status` mutation on top of a tier).
- The loose read path survives as a first-class named scenario rather than an implicit
  property of the small tier.
