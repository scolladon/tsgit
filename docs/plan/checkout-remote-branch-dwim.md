# Plan — checkout-remote-branch-dwim

> Source: design doc docs/design/checkout-remote-branch-dwim.md · Rulings ADR-1281 (DC-1 `guess?: boolean`),
> ADR-1282 (DC-2 `createdBranch?: BranchCreateResult`), ADR-1283 (DC-3 three new codes, R9c reuses
> `INVALID_OPTION createBranch`), ADR-1284 (DC-4 `checkout.guess` joins the eager line-order race),
> ADR-1285 (DC-5 B: `force` routes to the plain restore, U2 to the ledger), ADR-1286 (DC-6 no new perf
> gate, `bench:ab` after), ADR-1287 (DC-7 `feat(checkout):` for `guess` and `createdBranch`, no `!`).
> The plan is the implementation script AND the knowledge handoff. Part agents start
> with zero context: whatever a part block omits is paid later as agent rediscovery.
> `plan-lint.sh` enforces the schema below — the plan phase cannot close without it.

## Sizing rules

- Every part costs a full agent lifecycle (spin-up, zero-context rebuild, gate) — it
  must earn it. No standalone test-only parts for FEATURE code: coverage/interop/property
  tests fold into the implementation part whose code they exercise. EXCEPTION:
  test-infra-only and docs-only parts (tooling config, test helpers, fixtures,
  harness/ADV/property suites, docs/prose) with no `src/` delta ARE standalone — they
  have no implementation part to fold into.
- A part that would be a pure test pass over already-landed code merges into its
  neighbour.
- A part should land in ~100 tool calls. More than ~5 RED→GREEN cycles, or more than 6
  files in its `### Context` block, is two parts. What counts is a path in backticks:
  backtick the files the part CREATES or EDITS, and write read-only reference paths in
  plain text.

## Shared facts (every part reads this first)

Binding for every part: GWT split across describe/it, AAA comments, `sut`, 100 % coverage,
mutation-resistant assertions (try/catch + `.data`, one guard per row), no call-count spies
(lesson 011: prove "not reached" by outcome), no suppression comments of any kind (no
`cspell:ignore` either: a new word goes into cspell.json, which only Part 4 carries — spell
test arguments with dictionary words such as `nope`, `missing`, never run-together non-words), no
phase/ADR/backlog ids in src or test, no swallowed errors. Implementers have no MCP tools:
read the ranges named below directly.
